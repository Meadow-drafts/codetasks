# CodeTasks — Feature & Version Implementation Roadmap

You are working inside the CodeTasks VS Code extension repository.

You have direct access to the IDE, repository files, TypeScript source, package configuration, extension manifests, and existing implementation. You should inspect the repository before making changes and treat the existing code as the source of truth.

This document defines the **planned product evolution and implementation order**.

Do not implement every future feature immediately. Work version by version, preserving existing functionality and architecture.

---

# 1. PRODUCT PURPOSE

CodeTasks is a VS Code extension that scans source code for developer task markers such as:

* TODO
* FIXME
* BUG
* HACK
* REFACTOR
* TASK

It turns these comments into persistent, manageable tasks.

The extension is intended to evolve from a simple code-comment task tracker into a more complete developer task-management/workflow tool inside VS Code.

The core principle is:

> CodeTasks should remain tightly connected to the source code while providing increasingly powerful task-management capabilities.


# 3. CURRENT TASK LIFECYCLE

A task can conceptually move through:

```text
Discovered
   ↓
Open
   ↓
In Progress
   ↓
Review
   ↓
Done
```

It can also become:

```text
Blocked
```

independently of the normal workflow.

A task can be:

```text
Active
   ↓
Archived
```

Archived tasks should not appear in active task lists.

Important distinction:

### Status

Describes workflow state:

```text
open
in-progress
blocked
review
done
```

### Priority

Describes importance:

```text
low
medium
high
critical
```

### Archive

Archive is NOT a status.

It is represented separately through:

```ts
archivedAt?: string;
```

Therefore:

```text
status = done
archivedAt = undefined
```

means a completed but active task.

Whereas:

```text
status = done
archivedAt = "2026-..."
```

means an archived task.

# 4. CURRENT FUNCTIONALITY

The implementation already contains or is expected to contain:

## Task discovery

Scan source files and identify task comments.

## Task reconciliation

The reconciler must preserve user-owned metadata when rescanning.

Existing task values that must survive rescanning include:

```text
status
priority
createdAt
updatedAt
archivedAt
```

Do not accidentally reset these when a source file is rescanned.

## Task persistence

Tasks are persisted through:

```ts
workspaceState
```

## Active task filtering

The canonical active-task definition is:

```ts
!task.archivedAt
```

The canonical archived-task definition is:

```ts
!!task.archivedAt
```

Do not duplicate alternative archive logic throughout the UI.

Use the TaskStore methods wherever possible.

# 6. IMPORTANT CURRENT BUG/ARCHITECTURE REQUIREMENT

The TaskStore emits:

```ts
this.changeEmitter.fire();
```

after modifications.

Consumers should subscribe to:

```ts
taskStore.onDidChange(...)
```

The workspace provider already listens for changes and refreshes:

```text
stats
tasks
```

The task detail page may also subscribe to store changes where appropriate.

The intended reactive flow is:

```text
User action
   ↓
TaskStore mutation
   ↓
save()
   ↓
changeEmitter.fire()
   ↓
UI subscribers
   ↓
UI refresh
```

Do not solve state-refresh problems by manually duplicating mutation logic in every webview.

# 14. ARCHITECTURAL RULES FOR ALL FUTURE VERSIONS

## Rule 1 — TaskStore is the source of truth

UI must not become the source of truth.

Correct:

```text
UI
 ↓
TaskStore
 ↓
Persistence
 ↓
onDidChange
 ↓
UI
```

Incorrect:

```text
UI
 ↓
change local HTML
 ↓
hope persistence catches up
```

---

## Rule 2 — Do not duplicate business logic

Do not implement archive behavior independently in:

* workspace provider
* detail provider
* archived provider
* commands

Instead:

```ts
taskStore.archiveTask(taskId)
```

should be the central operation.

---

## Rule 3 — Reconciliation must preserve user state

When scanner output changes, do not overwrite:

```text
status
priority
createdAt
updatedAt
archivedAt
```

unless there is a deliberate product reason.

---

## Rule 4 — Active and archived tasks are different views

Use:

```ts
getActiveTasks()
```

for active UI.

Use:

```ts
getArchivedTasks()
```

for archive UI.

Use:

```ts
getTasks()
```

only when intentionally working with the complete dataset.

---

## Rule 5 — UI refresh must be event-driven

After successful mutations:

```ts
this.changeEmitter.fire();
```

Consumers should react to the event.

Avoid manually forcing every webview to reconstruct state independently.

---

## Rule 6 — Preserve existing functionality

Before changing a shared component, inspect all consumers.

For example, changing:

```ts
getTasks()
```

may affect:

* workspace
* detail page
* archived page
* scanner
* commands
* statistics
* reconciliation

Do not change semantics without checking callers.

```text

existing task → preserved
status preserved
priority preserved
```

```text

→ active list excludes task
→ archived list includes task
```

```text
→ active list includes task
```

# 17. DO NOT DO THESE THINGS

Do not:

* rewrite the architecture unnecessarily
* introduce Redux/Zustand/etc. for webviews without need
* introduce a backend prematurely
* replace workspaceState without a requirement
* duplicate TaskStore logic
* create separate archive state in the webview
* hide archived tasks only with CSS
* make scanner reconciliation overwrite user state
* introduce AI before core functionality is stable
* implement future roadmap features without being asked
* break existing commands while adding features
* remove working functionality during refactoring

```text

Files affected
Business logic changes
UI changes
Event/state synchronization changes
Tests required
```
